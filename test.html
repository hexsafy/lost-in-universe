Constant Time, Predictable Performance

September 16, 2025 Carlo Hexsafi

Here is a function to divide two integers by repeated subtraction.

long long divide_by_subtraction(long long dividend, long long divisor) {
    // O(N) wrt quotient's magnitude
    long long quotient = 0;
    while(dividend >= divisor) {
        dividend -= divisor;
        quotient++;
    }
    return quotient;
}
// Note: I've ommited sign-related edge case handling for clarity.

This code is correct. It is also slow. Calculating 2,147,483,647 / 2 requires the while loop to run over a billion times, which can take several seconds on a modern CPU. The processor's built-in DIV instruction does the same work in a single clock cycle (~0.29 nanoseconds).

An improvement is to subtract in powers of two.

long long divide_by_doubling(long long dividend, long long divisor) {
    // O(log n)
    long long quotient = 0;
    while (dividend >= divisor) {
        long long temp = divisor;
        long long multiple = 1;
        while ((dividend - (temp << 1)) >= 0) {
            temp <<= 1;
            multiple <<= 1;
        }
        dividend -= temp;
        quotient += multiple;
    }
    return quotient;
}

This version reduces the billion-iteration case to about 30 iterations. The performance is now logarithmic. The execution time, however, still depends on the input values. 10 / 3 takes fewer iterations than 1,000,000,000 / 3. The performance is not predictable as the execution time is still variable.

This unpredictability can cause failures in certain systems. A hard real-time system's correctness depends on both the logical result of a computation and the time at which it is produced.

Consider a car's ECU (Engine Control Unit). It runs a control loop that must complete within a strict time budget, perhaps 5 milliseconds, before the crankshaft physically rotates to the next firing position. If a calculation within that loop takes longer on some inputs than others, the commands to the fuel injectors can be sent late. A late command causes an inefficient combustion cycle or a misfire. For these systems, Worst-Case Execution Time (WCET) is a physical requirement.

Result by Construction

To get predictable performance, the number of operations must be constant. This requires reframing the problem. Instead of asking "How many times can I subtract the divisor?", we can ask "What is the binary representation of the quotient?" then we can construct it bit by bit. The goal is to determine the value of each of the 32 bits in the quotient, from most significant to least significant.

For each bit position i, we check if divisor * 2^i fits into the remaining dividend. If it does, the i-th bit of the quotient is 1 and we subtract. If not, the bit is 0.

Here is the process for dividing 13 (1101) by 3 (11):

Dividend: 1101 (13), Divisor: 11 (3), Quotient: 0000

Step 1 (i=3): Does (11 << 3) fit in 1101? (24 > 13) -> No.
         Quotient is still 0000

Step 2 (i=2): Does (11 << 2) fit in 1101? (12 <= 13) -> Yes.
         Subtract:   1101 - 1100 = 0001
         Set bit 2:  Quotient is now 0100

Step 3 (i=1): Does (11 << 1) fit in new dividend 0001? (6 > 1) -> No.
         Quotient is still 0100

Step 4 (i=0): Does (11 << 0) fit in 0001? (3 > 1) -> No.
         Quotient is still 0100

Final Quotient: 0100 (binary) = 4. Remainder = 1.

This sequence translates directly into code:

long long divide_by_construction(long long dividend, long long divisor) {
    long long quotient = 0;
    for (int i = 31; i >= 0; --i) {
        if ((divisor << i) <= dividend) {
            dividend -= (divisor << i);
            quotient |= (1LL << i);
        }
    }
    return quotient;
}

This for loop always runs 32 times for 32-bit integers. The execution path is identical for every possible input. The performance is constant.

 Case study: ARM Cortex-M4

To see what this predictability means in practice, we can estimate the cycle counts on a common embedded processor, an STM32F401RE (ARM Cortex-M4 CPU), clocked at 100MHz (one cycle is 10 nanoseconds).

- divide_by_subtraction - the naive O(N) approach: The loop body is ~4-5 cycles. For 2,147,483,647 / 2, this is 1.07B iterations * 4 cycles per iteration ≈ 4.28 billion cycles. At 100MHz, that is 42.8 seconds.

- divide_by_doubling - the clever O(log N) approach: The worst case might be ~1800 cycles (18 microseconds). The best case for small numbers might be ~50 cycles. The jitter between best and worst case is over 30x.

- divide_by_construction the constant-time O(1) approach: The loop body is ~5 cycles. The total time is 32 iterations * 5 cycles/iter = 160 cycles. This is 1.6 microseconds. Every single time.

The constant-time algorithm is faster in the worst case and has zero performance jitter. You can build a reliable system around that guarantee. The actual hardware is even more direct, often using a specialized SRT divider circuit. . The constant-time software algorithm is an abstraction that mirrors this physical reality.

The final algorithm is better because its structure has the same shape as the underlying hardware: a fixed-depth series of simple operations. This principle is broadly applicable. A ring buffer is effective because its contiguous memory layout works with the CPU's prefetcher. A sorting network can be faster than quicksort for small, fixed inputs because it compiles to branchless code that keeps the CPU pipeline full.

This process of thinking by construction, bit by bit, similar to how the machine works is a useful tool for writing reliable, constant-time code. The division problem is just a convenient puzzle for putting this mindset to the test. If you want to give it a try yourself, I'd highly recommend trying out the exact problem that motivated this post on LeetCode.
